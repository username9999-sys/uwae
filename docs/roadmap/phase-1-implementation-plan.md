### Added by the INSTRUCTION.md mandate (absent from the original plan)

- Access assessment/classifier: three independent state machines (origin, session, job), evidence model, reason codes (Access Control Plane spec).
- Adaptive strategy planner (deterministic, evidence-based decisions).
- Session recovery protocol (`SessionRecoveryProvider` contract).
- Bounded retries with reason codes — mandatory; the baseline's unbounded retry is a reproduced defect (E6) and the concrete differentiator.
- Benchmark dimensions beyond success/failure: diagnosis quality and decision quality.

### Pasca-roadmap integration (2026-10-21)

- **Worker ↔ ACP wiring complete**: `core/job_worker.py` now runs the Spec v2 §1 cycle per attempt (Observe → Diagnose → Decide → Execute): transport results/failures become bounded-signal observations (`http.status`, `network.error`, `body.marker.target`) → `access.classifier` (ADR-012) → `access.planner` (ADR-013) → the worker acts. Terminal decisions: ACCEPT (SUCCEEDED — requires classifier `ACCESS_GRANTED`, never a bare 200), NEEDS_USER (explicit denial 403 — never auto-retried, ACP §2.2), ABORT (FAILED with reason code). The worker has no retry policy of its own anymore.
- **Planner budget gates closed (G4)**: `RECOVER_SESSION` (AUTH_REQUIRED) and the `USE_BROWSER` paths (CHALLENGE_PRESENT/JAVASCRIPT_REQUIRED) were unguarded — a persistent 401 would loop forever once the worker consumed the planner. All escalation actions are now budget-gated (3 new planner tests).
- **Worker integration tests**: `tests/test_worker_acp.py` (7 tests with fake adapters: validated success, denied → NEEDS_USER, 429 bounded → BUDGET_EXHAUSTED, transport escalation switch → SUCCEEDED, all-transports-exhausted → ABORT, empty 200 → no false success, persistent 401 → bounded).
- **Browser path wired (ADR-014)**: `browser/adapter.py` (`CDPBrowserAdapter`, raw CDP per ADR-011 decision 4 — zero new deps) executes the planner's `USE_BROWSER` decision; `JobWorker(browser_adapter=...)` gates `browser_available`; bounded content-marker detection (JS gates, challenge interstitials) makes `JAVASCRIPT_REQUIRED`/`CHALLENGE_PRESENT` reachable from real responses; the /js fixture is now a true JS gate (gate text replaced by the page script at render). End-to-end proof: HTTP fetch → JS-gate → chromium render → validated content → SUCCEEDED (`TestBrowserRealCDP`).
- **Session persistence (SQLite, §5.1)**: `session/store_sqlite.py` (`SqliteSessionStore`, kontrak identik dengan `SessionStore` — manager tak berubah) — generasi berversi + status bertahan lintas restart proses; materi rahasia (cookies/token) tidak pernah ditulis ke disk (batas §6.3 — pasca-restart entry dimuat dengan `session=None`, protokol recovery meng-autentikasi ulang secara berbatas); disiplin transisi durabel (republish saat ACTIVE ditolak pasca-restart); aturan resume generasi (G5) terverifikasi melalui `SessionRecoveryManager` sungguhan; 10 tests in `tests/test_session_store_sqlite.py`.
- **Milestone B — harness evaluasi classifier (G3)**: `access/observe.py` (satu sumber kebenaran pembangun observasi — worker produksi & harness memakai kode yang sama) + `benchmark/classifier_eval.py` — korpus berlabel 24 kasus mencakup seluruh 9 kelas + preseden urutan §3.1 + robustness; hasil terukur: akurasi **1.00** (24/24, mismatch 0, confusion matrix hanya diagonal, precision/recall **1.00** per kelas), proporsi UNKNOWN 2/24 terukur; probe marker 5/5 (FP-guard: kata "captcha"/"javascript" dalam artikel normal terhindar; TP: gerbang JS + interstitial challenge); 3 kasus turunan respons fixture nyata (/html→granted, /missing→content_invalid, /js→javascript_required); laporan + daftar keputusan tak-terputuskan di `docs/benchmark/classifier-evaluation.md`; 13 tests in `tests/test_classifier_eval.py`.
- **G6 durability — crash recovery (§5.2)**: `core/job_repository.py` gains `attempts` + `job_events` tables (§5.1) with `start_attempt`/`finish_attempt`/`latest_attempt`/`list_attempts`/`record_event`/`list_events`/`recover_interrupted`; the worker records every attempt RUNNING **before** execution with unique per-run attempt ids (re-execution after a crash never overwrites the audit trail); recovery rules: RUNNING attempt → INTERRUPTED + re-queue within the job's cross-restart retry budget (else FAILED budget_exhausted), SUCCEEDED attempt + artifact → job completed **from evidence** (no re-acquisition, no duplicate artifact — A10), NEEDS_USER never auto-recovered (ACP §2.2), terminal jobs untouched; `JobWorker.start()` recovers before picking new work; 13 tests in `tests/test_durability.py` (crash → recover → re-execute leaves the attempt trail `interrupted → succeeded`).
- **Skenario diagnosis §6.1 (A04/A06/A07/A11)**: fixture server +5 endpoint deterministik (`/login`, `/rate-limited` 429+Retry-After, `/denied`, `/challenge` 403+interstitial, `/invalid-html`); `TransportFailure` kini membawa headers+body (dipotong 4 KB) sehingga worker membedakan 429+Retry-After, 403 polos, dan interstitial 403+signature — bukan sekadar "HTTP error"; observer mendeteksi form login (A04), menghormati Retry-After dari server (A06), membedakan challenge vs denial dari body kegagalan (A07), dan menolak HTML tak terurai sebagai konten target (A11); verifikasi menangkap + memperbaiki bug nyata (jalur kegagalan memancarkan `target=found` → ACCEPT dengan artifact None — diperbaiki via `allow_target_found=False`); 4 test eval + 5 test skenario worker.

## Phase 1 Goals
The goal of Phase 1 is to implement a minimal but functional web acquisition engine that demonstrates the core architecture concepts validated in Phase 0. This includes:

1. Core job model with durable state management
2. HTTP acquisition capability (as the primary transport)
3. Basic artifact pipeline with storage and integrity verification
4. Simple discovery capability (seed URLs and basic HTML link extraction)
5. Minimal CLI interface for job submission and monitoring
6. Basic benchmarking capability to measure against Botasaurus baseline

## Implementation Sequence

Phase 1 will be implemented in the following sequence, with each step building upon the previous:

### Step 1: Project Setup and Core Infrastructure
- Create project structure with proper Python packaging
- Implement configuration management system
- Set up logging and basic observability
- Create basic CLI framework
- Implement core utilities (UUID generation, timestamping, etc.)
- Create base classes and interfaces

### Step 2: Core Job Model Implementation
- Implement SQL schema for job state persistence
- Create job state machine with defined states
- Implement job repository for storage operations
- Build job scheduler and worker pool
- Add attempt tracking and basic retry logic
- Implement job cancellation and cleanup

### Step 3: HTTP Transport Adapter
- Implement HTTP adapter using httpx (with requests fallback)
- Create adapter interface and registry
- Implement acquisition request/response models
- Add support for headers, timeouts, redirects, cookies
- Implement basic proxy support
- Add response streaming capability for large files
- Implement basic metrics collection (timing, status codes, etc.)

### Step 4: Artifact Pipeline Foundation
- Implement artifact model and metadata schema
- Create local filesystem artifact storage
- Implement fixity verification (SHA-256 hashing on store and verify)
- Build basic artifact service for storage and retrieval
- Implement basic identification by file extension (placeholder for future enhancement)
- Create artifact lifecycle coordination (store → identify)

### Step 5: Basic Discovery Engine
- Implement seed URL discovery source
- Create basic HTML link extractor (using BeautifulSoup or lxml)
- Implement URL normalization and deduplication
- Create simple discovery queue feeding jobs to the scheduler
- Add basic scope filtering (domain allow/block lists)
- Implement basic robots.txt parsing and compliance

### Step 6: Minimal CLI Interface
- Implement job submission command (specify URLs, options)
- Implement job listing command (show recent jobs and status)
- Implement job details command (show job metadata and results)
- Implement job cancellation command
- Implement benchmark command to run predefined scenarios
- Implement help and version commands

### Step 7: Initial Benchmark Suite
- Implement at least 3 deterministic benchmark fixtures:
  1. Simple HTTP GET fixture (small text file)
  2. HTML link discovery fixture (page with known links)
  3. Basic JavaScript detection fixture (page requiring JS for content)
- Create benchmark runner that executes fixtures against both engines
- Implement result collection and basic comparison reporting
- Document baseline measurements from Botasaurus for comparison

### Step 8: Integration and Testing
- Wire all components together through dependency injection
- Implement end-to-end test scenarios
- Add basic error handling and logging throughout
- Create documentation for usage and configuration
- Run benchmarks against both engines to validate approach

## Dependencies Between Steps

Each step depends on the completion of previous steps:
- Step 2 (Job Model) depends on Step 1 (Project Setup)
- Step 3 (HTTP Adapter) can proceed in parallel with Step 2 but benefits from Job Model for persistence
- Step 4 (Artifact Pipeline) depends on Job Model for persistence context
- Step 5 (Discovery) depends on Job Model to create jobs for discovered URLs
- Step 6 (CLI) depends on all previous components to expose functionality
- Step 7 (Benchmark) depends on having a minimally functional engine to test
- Step 8 (Integration) depends on all previous steps being implemented

## Acceptance Criteria for Phase 1 Completion

Phase 1 is complete when the following criteria are met:

### Functional Criteria
- [ ] Engine can accept a URL via CLI and acquire it successfully
- [ ] Acquired resources are stored as artifacts with fixity verification
- [ ] Job status can be queried through CLI throughout the lifecycle
- [ ] Failed jobs can be identified and inspected for error details
- [ ] Successfully acquired content matches expected byte-for-byte content
- [ ] Artifacts can be retrieved by ID and verified against original source
- [ ] Basic HTML link discovery works and creates follow-on acquisition jobs

### Performance Criteria
- [ ] Engine completes simple HTTP GET acquisition within 5 seconds (on localhost)
- [ ] Memory usage during acquisition remains under 50MB for small resources
- [ ] CPU usage returns to near-idle levels after acquisition completion
- [ ] Storage overhead for metadata is less than 20% of acquired data size
- [ ] Benchmark shows comparable or better success rate than Botasaurus for simple HTTP GET

### Reliability Criteria
- [ ] Engine handles network timeouts gracefully (does not hang indefinitely)
- [ ] Engine recovers correctly from SIGTERM (graceful shutdown)
- [ ] Engine preserves job state across process restarts for incomplete jobs
- [ ] Engine does not create duplicate artifacts for the same acquisition job
- [ ] Engine correctly handles HTTP redirect chains (301, 302, etc.)
- [ ] Engine respects basic robots.txt disallow rules

### Usability Criteria
- [ ] CLI provides helpful error messages for incorrect usage
- [ ] CLI shows meaningful progress during long-running acquisitions
- [ ] CLI job details show acquisition timestamps, sizes, and status
- [ ] Help text is available for all commands
- [ ] Version information is accessible via CLI

### Extensibility Criteria
- [ ] HTTP adapter follows the defined adapter contract
- [ ] Artifact storage follows the defined storage interface
- [ ] Discovery sources follow the defined source interface
- [ ] New adapters/sources can be added without modifying core logic
- [ ] Configuration system allows overriding of default values

## Risks and Mitigations

### Technical Risks
1. **Risk**: Performance overhead from persistence layer impacts acquisition speed
   - **Mitigation**: Use write-ahead logging, batch commits, and async writes where possible
   - **Verification**: Benchmark persistence overhead and optimize as needed

2. **Risk**: Complexity of state management leads to bugs in job lifecycle
   - **Mitigation**: Implement comprehensive state transition testing
   - **Verification**: Test all state transition paths and edge cases

3. **Risk**: Storage corruption leads to data loss
   - **Mitigation**: Implement fixity checks on read and write, consider journaling
   - **Verification**: Test recovery from simulated storage corruption

### Resource Risks
1. **Risk**: Memory leaks in long-running engine
   - **Mitigation**: Implement resource tracking and regular garbage collection
   - **Verification**: Run long-soak tests and monitor memory usage

2. **Risk**: File descriptor limits exceeded during concurrent operations
   - **Mitigation**: Implement connection pooling and resource limits
   - **Verification**: Test with high concurrency and monitor resource usage

### Schedule Risks
1. **Risk**: Underestimation of complexity in any individual step
   - **Mitigation**: Time-box each step and adjust scope based on learnings
   - **Verification**: Regular review of progress against planned schedule
